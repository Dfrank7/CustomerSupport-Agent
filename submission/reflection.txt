I implemented cross-session memory as a MemoryHook instead of pasting customer facts into the system prompt. The hook registers two callbacks. Before each turn, retrieve_customer_context queries every memory-strategy namespace for the current customer and prepends those records to the user message. After the agent answers, save_support_interaction stores the customer query and the assistant reply through memory_client.create_event(). Keeping retrieval and persistence in one HookProvider means every invoke path, including AgentCore Runtime, gets the same behavior without extra steps in the entrypoint. In session A the agent stored that the customer is Jane and prefers concise responses. After waiting for extraction, a new session with the same customer ID recalled both facts, which confirmed that the namespaces and actor ID were wired correctly.

The deployment failure was a packaging problem, not a model error. agentcore deploy installs dependencies for Linux ARM64 with uv and disables source builds. The lockfile had resolved lazy-object-proxy 1.13.0, a release that ships macOS and Windows wheels only. That package is pulled in by openapi-spec-validator through bedrock-agentcore-starter-toolkit, so the agent never imported it directly, but the deploy still required a Linux wheel. I pinned lazy-object-proxy==1.12.0, which includes a cp313 manylinux2014_aarch64 wheel, regenerated the lock, and redeployed. The package uploaded and the runtime became ready.

I would not leave the Gateway on the NONE authorizer in production. That setting let the lab agent call order tracking and refunds without a bearer token, which is acceptable only while the gateway is temporary and carries no sensitive traffic. A real deployment should require authentication on the gateway, restrict the execution role to the specific knowledge base and memory ARNs, and delete the gateway, memory, knowledge base, and OpenSearch Serverless collection after the exercise so unused vector storage does not keep billing.
